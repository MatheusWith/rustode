# ADR 0030: The debug adapter client starts with a tracer: launch, breakpoints, stop and continue, over the LSP child-process supervision

- **Status:** accepted (2026-11-19). The owner decided on the adapter setting `rustode.debugAdapters` on 2026-11-19: "pode ser e lembre-se de ser modificável" (it is fine, and it must be modifiable). Proposed 2026-11-19 with ticket 37; extended by ticket 38.
- **Build:** rustode after `753a255`, extended by ticket 38 (stepping and the views, below); studied: the source tree of the App (local VSCodium 1.147.0)

## Context

Milestone M7 is debugging over the Debug Adapter Protocol ([ADR 0018](0018-phase-1-milestones.md)). [ADR 0015](0015-child-process-servers.md) decided that debug adapters, like language servers, run as child processes over stdio, supervised by the workspace, and that the LSP client proves the supervision first. DAP frames its messages as LSP does (`Content-Length`, a blank line, JSON), so the process, the framing and the traces can be shared.

The first slice is a tracer: one path through every layer, so later tickets (stepping, call stack, variables, console: ticket 38) add to a working client. The path is the one VS Code takes when F5 is pressed (`src/vs/workbench/contrib/debug/browser/debugSession.ts:395-406`, `:1065-1090`): `initialize`, `launch`, and when the adapter says `initialized`, `setBreakpoints` for every file and `configurationDone`.

## Decision

The DAP client lives in `crates/workspace/src/dap/` and reuses the child-process supervision of the language servers, factored out of `lsp/` into `crates/workspace/src/child/` instead of copied: the process with its writer, reader and stderr threads, the waker, the framing, and the shutdown wait and reap steps. The LSP code behaves as before.

Containment rules:

1. **Configuration.** Launch configurations are read from `.vscode/launch.json` of the opened folder (`debugConfigurationManager.ts:646`), in VS Code's format, with `rustode-config`'s JSONC parser. A syntax error, a bad entry or an unreadable file is a problem reported by `Workspace::debug_problems`, never a failure; the entries that are fine still work. Every property of an entry goes to the adapter as the arguments of `launch`, as VS Code does. Only `${workspaceFolder}` and `${workspaceFolderBasename}` are substituted so far.
2. **Which adapter.** VS Code's debuggers come from extensions, and rustode has no extension host. The adapter for a configuration `type` is set in `settings.json`, in the shape of `rustode.languageServers`: `"rustode.debugAdapters": { "lldb": { "command": "lldb-dap", "args": [] } }` (`crates/workspace/src/dap/settings.rs`). A type with no adapter is refused with a message that names the setting. No adapter is bundled and no proprietary one is used (ADR 0015 rule 5).
3. **Session.** One session at a time. `start_debugging`, `continue_debugging` and `stop_debugging` return an error that says why they were refused. Stopping asks for `terminate` when the adapter supports it, else `disconnect` with `terminateDebuggee`, as `debugSession.ts:420-445` does; asked twice, the session is dropped. The adapter's `terminated` event ends the session with a `disconnect`; the adapter's exit code message and the program's exit code are kept as `DebugStatus::message`.
4. **A crashed adapter is reported and not restarted.** Unlike a language server, restarting an adapter would run the program again. The session ends with `the debug adapter exited with code N` and a new session can be started by hand.
5. **Breakpoints** belong to the workspace, by absolute path and zero-based line; DAP's lines are one-based and converted at the boundary (`linesStartAt1`). Setting one while a session runs sends that file's breakpoints again. They do not follow edits and are not saved across runs yet.
6. **Commands** are registered in `COMMANDS` with VS Code's ids and keys: `workbench.action.debug.start` (F5), `workbench.action.debug.continue` (F5 while stopped), `workbench.action.debug.stop` (Shift+F5) and `editor.debug.action.toggleBreakpoint` (F9). `Workspace::debug_key_command` says which of start and continue F5 means now, so the frontends hold no `when` logic. The frontends add a click on the gutter, which calls `Workspace::toggle_breakpoint`.
7. **Adapter messages are hostile input.** Every field is read with a checked accessor, a thread id outside `0..=i32::MAX` and a line below 1 are ignored, texts are cut at 500 characters, a response nobody asked for and an unknown message are ignored, the table of requests waiting for an answer is bounded, and the adapter's own requests (`runInTerminal`) are answered with a refusal so it does not wait for us.
8. **Tests** use `rustode-test-dap` (`crates/test-dap`, `publish = false`), a stdio adapter whose program is a text file (a breakpoint stops it before a line; `CRASH` exits with code 3; `HOSTILE` sends malformed messages). It answers `launch` only after `configurationDone` and sends `initialized` when `launch` arrives, so a client that gets the order wrong fails. The seams are the workspace API (`crates/workspace/tests/dap.rs`), the TUI's test backend (`crates/tui/tests/debug.rs`) and egui_kittest (`crates/gui/tests/frame/debug.rs`).

## Ticket 38: stepping, the call stack, variables, watch and the console

The client keeps what a stopped program shows (`crates/workspace/src/dap/model.rs`, `views.rs`) and both frontends draw it. The setting `rustode.debugAdapters` is unchanged and, since the owner's decision below, accepted.

9. **Order at a stop.** On `stopped` the client asks for `threads` and `stackTrace` (levels capped at 100); the stack's reply selects the top frame, moves the editor to its line (the file is opened if it is a regular file of at most 64 MiB) and asks for the frame's `scopes`; the first scope that is not `expensive` opens by itself (`variablesView.ts:110-112`); every watch expression is evaluated with context `watch` for the frame. Other variables are asked for when the user expands them (lazy expansion through `variablesReference`). Picking another frame repeats the scopes and the watch evaluations for it and moves the editor.
10. **Versions instead of locks.** Execution moving on (`continue`, a step, a `continued` or `stopped` event) forgets the threads, frames, scopes and variables and drops every request still waiting for an answer about them from the table of pending requests; picking another frame drops the ones about the old frame. An answer that arrives later finds no request waiting and is ignored (`an answer nobody asked for`), so stale data is never applied. That also means a request an adapter never answers cannot pile up across stops. Console evaluations are kept: their answer is wanted whenever it comes.
11. **Bounds, since replies are hostile.** At most 64 threads, 100 frames, 8 scopes, 200 variables per reply, 2,000 nodes per tree, 32 watch expressions and 1,000 console lines; names, values and messages are cut at 500 characters; ids and references outside `0..=i32::MAX` are refused, and a variable that is not a string-named object is skipped; a variable can be expanded to depth 8 only, which ends an adapter's cycle of references; at most 256 requests wait for an answer and past that the client refuses with "the debug adapter has too many requests waiting"; a failed or cancelled `variables` request leaves the node empty, a failed `evaluate` shows the adapter's message as the watch's value or as a console error. A `continue` or step the adapter refuses reads the stop's state again and says why.
12. **Commands** use VS Code's ids and keys, each with VS Code's `when` clause (`debugCommands.ts:500-560`): `workbench.action.debug.stepOver` F10 (`debugState == 'stopped'`), `stepInto` F11 (`debugState != 'inactive'`), `stepOut` Shift+F11 (`debugState == 'stopped' && threadHasMultipleStackFrames`), `pause` F6 (`debugState == 'running'`). `Workspace::command_applies` evaluates the clause with the `rustode-config` evaluator, so the frontends hold no `when` logic: they ask it and, when it does not hold, the key keeps its other meaning. That resolves F6, which both frontends use for "focus next part": it pauses while the program runs and moves the focus otherwise. Watch commands: `workbench.debug.viewlet.action.addWatchExpression` and `debug.removeWatchExpression` (frontend prompts and selection), `workbench.debug.viewlet.action.removeAllWatchExpressions` (workspace), and the four focus commands `workbench.debug.action.focusCallStackView`, `focusVariablesView`, `focusWatchView` and `focusRepl`.
13. **Frontends.** TUI: a four-column panel below the editor while a session exists (`crates/tui/src/debug.rs`; Tab and Shift+Tab move between columns, Enter picks, opens or evaluates, Delete removes a watch, Escape leaves). GUI: the same four columns in egui (`crates/gui/src/debug.rs`); every row is a button for screen readers. The watch values and the console live in the workspace, so a restart of the frontend would lose nothing the session had.
14. **Tests.** `rustode-test-dap` grew a deterministic program language (`enter`, `leave`, `var`, `obj`, `global`, `print`, `error`, `console`, `WAIT`) that gives the call stack, the variables (objects nest, and one can point at itself), `evaluate` (`!cancel` fails with "cancelled", `!hang` is never answered), `next`, `stepIn`, `stepOut` and `pause`, and the option `--hostile-replies` that answers with oversized and malformed bodies. Tests: `crates/workspace/tests/dap.rs` (the workspace seam, including `what_arrives_after_execution_moved_on_is_dropped`, `a_reply_that_never_comes_is_bounded_and_does_not_block`, `hostile_replies_are_bounded_and_do_not_derail_the_session` and `a_cycle_of_objects_expands_only_to_the_depth_limit`), `crates/tui/tests/debug.rs` and `crates/gui/tests/frame/debug.rs` (snapshots of the stopped state with the four views).

## Owner decision: `rustode.debugAdapters` stays, and is freely modifiable

Decided by the owner on 2026-11-19. The setting is edited freely in `settings.json` and a change applies live, as `rustode.languageServers` does (`Workspace::reload_config` calls `dap_config_changed` next to `lsp_config_changed`):

15. An entry is `{ "command": ..., "args": [...], "env": {...} }`; `env` (strings only) is added to the adapter's environment. Types can be added, removed and changed at any time. The value read last is used at the **next** start; a running session keeps the adapter it started with (it owns the process), whatever happens to the setting. No restart of the editor is needed.
16. An entry set to `null` switches that type's adapter off, as #29 did for language servers. rustode ships no debug adapter, so there is no built-in default for a user entry to override; if one is ever added, the user's entry wins and `null` disables it, by the same rule. Today `null` and a missing entry both end in "no debug adapter for type ...; set rustode.debugAdapters[...]".
17. An invalid entry (not an object, no `command`, an empty one, `args` or `env` of the wrong type, an `env` value that is not a string, an unknown property) is a problem sentence in `Workspace::debug_problems`, counted with the other settings problems by both frontends, and the entry is skipped or its bad part ignored; the other entries still work. A setting of the wrong type altogether is also a settings diagnostic. Nothing here can crash. Tests (workspace seam): `a_changed_adapter_setting_applies_at_the_next_start_without_a_restart`, `a_session_keeps_its_adapter_when_the_setting_changes`, `invalid_adapter_entries_are_reported_and_the_valid_ones_still_work`.

## Ticket 39: conditional breakpoints, hit counts, logpoints and real adapters

Studied: `src/vs/workbench/contrib/debug/common/debugModel.ts:1040-1100` (the breakpoint's `condition`, `hitCondition`, `logMessage`, `verified`, `supported`), `browser/breakpointWidget.ts:92-94`, `:160-200`, `:215-217`, `:490-505` (one text shown at a time, all three kept), `browser/debugEditorActions.ts:101-215` (the three editor commands), `browser/debugSession.ts:488-520` (`setBreakpoints` and what is done with the answer) and `browser/breakpointsView.ts:1923-1960` (the icon and the message of an unsupported breakpoint). Reimplemented, see `ATTRIBUTION.md`.

18. **Model.** A breakpoint is a line with three optional texts (`crates/workspace/src/dap/breakpoints.rs`) and the state a session reported (`id`, `verified`, `message`). Texts are one line, trimmed, at most 1,000 characters; a line break or NUL is refused with `DebugError::BadBreakpoint`, an empty text is none. `Workspace::set_breakpoint` replaces what a line has, `toggle_breakpoint` still sets or clears (any kind), `breakpoint_details` and `breakpoint_at` give kind, texts, `verified` and the reason. The state belongs to the session: it is cleared when a session starts and ends.
19. **Capabilities.** `initialize`'s `supportsConditionalBreakpoints`, `supportsHitConditionalBreakpoints` and `supportsLogPoints` decide what is sent. VS Code sends all the texts and shows an unsupported breakpoint with a warning icon (`breakpointsView.ts:1923-1925`); the owner's ticket asks for a plain breakpoint that shows unverified with the reason, so a text the adapter does not support is not sent (the adapter would ignore it or refuse the breakpoint), the kind is kept for the gutter, and `breakpoint_details` says `verified: false` with "the debug adapter does not support conditional breakpoints" (or hit count conditions, or logpoints). With no session every breakpoint is shown verified.
20. **Verification** comes from the `setBreakpoints` response, matched by index as VS Code does (`debugSession.ts:512-519`), and from `breakpoint` events with reason `changed`, matched by the `id` the response gave. A refused request leaves the file's breakpoints unverified with the adapter's message. A response or event that is not what it should be (not an object, an id outside `0..=i32::MAX`, a `verified` that is not a boolean, a message past 500 characters) changes nothing or is cut. The line an adapter moves a breakpoint to is not followed yet.
21. **Commands** use VS Code's ids, with no default key (VS Code has none): `editor.debug.action.conditionalBreakpoint` ("Debug: Add Conditional Breakpoint..."), `editor.debug.action.addLogPoint` ("Debug: Add Logpoint...") and `editor.debug.action.editBreakpoint` ("Debug: Edit Breakpoint"). `debug.editBreakpoint`, which the ticket names, is VS Code's id for editing a *function* breakpoint's condition (`breakpointsView.ts:2353`), which rustode does not have; the editor action's id is used. The workspace keeps what the box needs: `begin_breakpoint_edit` gives a `BreakpointDraft` (the three texts, the choice shown; Edit opens on the text the line's breakpoint uses, as `breakpointWidget.ts:160-200`), the frontend edits it, `finish_breakpoint_edit` applies it.
22. **Frontends.** TUI: the quick input box on the cursor's line (`crates/tui/src/breakpoint.rs`); Tab shows the next of Expression, Hit Count and Log Message, the others keep what was typed, Enter applies, Escape cancels. GUI: the box of `crates/gui/src/navigate.rs` with the three names as buttons and a text field. Gutter marks: a disc for a plain breakpoint, a diamond for a condition or a hit count, a hollow diamond for a logpoint, in gray (a hollow disc for a plain one) when unverified; the stop's mark wins.
23. **Fixed for real adapters, each with a regression test against `rustode-test-dap`** (`crates/workspace/tests/dap.rs`, section "compatibility with real adapters"): `attach` configurations send `attach` and disconnect with `terminateDebuggee: false`, `terminate` is only asked for `launch` (`an_attach_configuration_sends_attach_and_stopping_leaves_the_program_alone`); an `initialized` event before the `initialize` response (not allowed, and survived) waits until `launch` was sent, one right after it (as lldb-dap does) works (`initialized_before_the_initialize_response_or_right_after_it_is_survived`); `initialize` says `supportsRunInTerminalRequest` and `supportsStartDebuggingRequest` are false and `supportsVariableType` true, and the adapter's `runInTerminal` and `startDebugging` get a failure with a reason that is also a console line (`the_adapters_own_requests_are_refused_with_a_reason_and_the_session_goes_on`); an adapter that exits after `exited` without `terminated` ends the session as a normal exit and not as a crash (`an_adapter_that_exits_after_exited_ends_the_session_normally`); a `stopped` event without `threadId` uses the first thread (`a_stop_without_a_thread_id_uses_the_first_thread`); the stop is matched with the open file through `canonicalize` when the adapter names the path another way (`the_stop_is_found_in_a_file_the_adapter_names_through_a_symlink`); relative paths in frames are resolved against the configuration's `cwd` (`a_relative_path_in_a_frame_is_resolved_against_the_configurations_cwd`). A palette taller than a short terminal panicked the TUI's drawing (`index outside of buffer`); found while testing the box, fixed (`the_palette_on_a_short_screen_draws_fewer_rows_instead_of_panicking`).
24. **Real adapters** are tested by `crates/workspace/tests/dap_real.rs`, `#[ignore]`d, one at a time, skipping themselves when `lldb-dap` is not on `PATH` or `python3` cannot import `debugpy`. Configuration, from the adapters' documentation: lldb-dap (`lldb/tools/lldb-dap/README.md`, "Launching a debugee" and the settings reference): `type` `lldb-dap`, `request` `launch`, `program`, `args`, `cwd`, `console: "internalConsole"` (since lldb-dap 21; the others need `runInTerminal`); debugpy (the wiki's "Debug configuration settings", launched as `python3 -m debugpy.adapter`): `type` `debugpy`, `request` `launch`, `program`, `args`, `cwd`, `console`, `justMyCode`. Each covers launch, a conditional breakpoint (`i == 3` in the fourth pass of a loop), the variables of the stop, an evaluation in the console, a step and the end; a second test per adapter stops the session while stopped. Every test ends its adapter and checks, by `/proc`, that no process is left. Results are in the pull request.
25. **Not done**, for later: following the line an adapter moves a breakpoint to; `runInTerminal` (an integrated terminal) and `startDebugging` (child sessions: debugpy's subprocesses are not debugged, and `subProcess` is left as the user set it); breakpoints that follow edits and survive a restart; function, data, exception and instruction breakpoints; validating hit count and condition syntax (the adapter judges, as in VS Code).

## The guarantee

A debug adapter that crashes, refuses a request or sends garbage ends or ignores the one message, and never takes the editor down or loses an open document. Confirmed by `an_adapter_that_sends_garbage_does_not_derail_the_session`, `a_crashing_adapter_is_reported_and_the_workspace_goes_on` and `a_launch_the_adapter_refuses_ends_the_session_with_its_reason`.

## Consequences

- Not done, and for later tickets: attach to a process the adapter does not launch is untested; several threads at once (only the stopped thread's frames are shown, and its `threadId` is the one stepped and paused); stepping by instruction or into targets; editing a variable's value; paging of variables past 200 and of frames past 100; a console with history, completion and ANSI colors; the watch of a selected expression from the editor; mouse use of the TUI panel; compound configurations; the other launch variables; breakpoints that follow edits and survive a restart; a picker for the configuration (the first one runs until `select_launch_configuration` is called); mutation tests of the DAP parser (AGENTS.md §11.7.1 rule 7: the parser reads `serde_json::Value`, which is checked by the hostile-adapter tests only, now including `--hostile-replies`).
- `cargo xtask` scopes: the new crate has no scope of its own; its commits use `workspace`, as `test-lsp`'s do.
- Anything else that needs a different adapter lifecycle (restart on crash, several sessions) requires a new decision, not an extension of this one.
