# ADR 0030: The debug adapter client starts with a tracer: launch, breakpoints, stop and continue, over the LSP child-process supervision

- **Status:** proposed (2026-11-19, ticket 37); the adapter setting `rustode.debugAdapters` is rustode's own and is the owner's to confirm
- **Build:** rustode after `753a255`, extended by ticket 38 (stepping and the views, below); studied: the source tree of the App (local VSCodium 1.147.0)

## Context

Milestone M7 is debugging over the Debug Adapter Protocol ([ADR 0018](0018-phase-1-milestones.md)). [ADR 0015](0015-child-process-servers.md) decided that debug adapters, like language servers, run as child processes over stdio, supervised by the workspace, and that the LSP client proves the supervision first. DAP frames its messages as LSP does (`Content-Length`, a blank line, JSON), so the process, the framing and the traces can be shared.

The first slice is a tracer: one path through every layer, so later tickets (stepping, call stack, variables, console: ticket 38) add to a working client. The path is the one VS Code takes when F5 is pressed (`src/vs/workbench/contrib/debug/browser/debugSession.ts:395-406`, `:1065-1090`): `initialize`, `launch`, and when the adapter says `initialized`, `setBreakpoints` for every file and `configurationDone`.

## Decision

The DAP client lives in `crates/workspace/src/dap/` and reuses the child-process supervision of the language servers, factored out of `lsp/` into `crates/workspace/src/child/` instead of copied: the process with its writer, reader and stderr threads, the waker, the framing, and the shutdown wait and reap steps. The LSP code behaves as before.

Containment rules:

1. **Configuration.** Launch configurations are read from `.vscode/launch.json` of the opened folder (`debugConfigurationManager.ts:646`), in VS Code's format, with `rustode-config`'s JSONC parser. A syntax error, a bad entry or an unreadable file is a problem reported by `Workspace::debug_problems`, never a failure; the entries that are fine still work. Every property of an entry goes to the adapter as the arguments of `launch`, as VS Code does. Only `${workspaceFolder}` and `${workspaceFolderBasename}` are substituted so far.
2. **Which adapter.** VS Code's debuggers come from extensions, and rustode has no extension host. The adapter for a configuration `type` is set in `settings.json`, in the shape of `rustode.languageServers`: `"rustode.debugAdapters": { "lldb": { "command": "lldb-dap", "args": [] } }` (`crates/workspace/src/dap/settings.rs`). A type with no adapter is refused with a message that names the setting. No adapter is bundled and no proprietary one is used (ADR 0015 rule 5).
3. **Session.** One session at a time. `start_debugging`, `continue_debugging` and `stop_debugging` return an error that says why they were refused. Stopping asks for `terminate` when the adapter supports it, else `disconnect` with `terminateDebuggee`, as `debugSession.ts:420-445` does; asked twice, the session is dropped. The adapter's `terminated` event ends the session with a `disconnect`; the adapter's exit code message and the program's exit code are kept as `DebugStatus::message`.
4. **A crashed adapter is reported and not restarted.** Unlike a language server, restarting an adapter would run the program again. The session ends with `the debug adapter exited with code N` and a new session can be started by hand.
5. **Breakpoints** belong to the workspace, by absolute path and zero-based line; DAP's lines are one-based and converted at the boundary (`linesStartAt1`). Setting one while a session runs sends that file's breakpoints again. They do not follow edits and are not saved across runs yet.
6. **Commands** are registered in `COMMANDS` with VS Code's ids and keys: `workbench.action.debug.start` (F5), `workbench.action.debug.continue` (F5 while stopped), `workbench.action.debug.stop` (Shift+F5) and `editor.debug.action.toggleBreakpoint` (F9). `Workspace::debug_key_command` says which of start and continue F5 means now, so the frontends hold no `when` logic. The frontends add a click on the gutter, which calls `Workspace::toggle_breakpoint`.
7. **Adapter messages are hostile input.** Every field is read with a checked accessor, a thread id outside `0..=i32::MAX` and a line below 1 are ignored, texts are cut at 500 characters, a response nobody asked for and an unknown message are ignored, the table of requests waiting for an answer is bounded, and the adapter's own requests (`runInTerminal`) are answered with a refusal so it does not wait for us.
8. **Tests** use `rustode-test-dap` (`crates/test-dap`, `publish = false`), a stdio adapter whose program is a text file (a breakpoint stops it before a line; `CRASH` exits with code 3; `HOSTILE` sends malformed messages). It answers `launch` only after `configurationDone` and sends `initialized` when `launch` arrives, so a client that gets the order wrong fails. The seams are the workspace API (`crates/workspace/tests/dap.rs`), the TUI's test backend (`crates/tui/tests/debug.rs`) and egui_kittest (`crates/gui/tests/frame/debug.rs`).

## Ticket 38: stepping, the call stack, variables, watch and the console

The client keeps what a stopped program shows (`crates/workspace/src/dap/model.rs`, `views.rs`) and both frontends draw it. The first decision above is unchanged: the adapter setting stays `rustode.debugAdapters` and this ADR stays *proposed* until the owner decides on it.

9. **Order at a stop.** On `stopped` the client asks for `threads` and `stackTrace` (levels capped at 100); the stack's reply selects the top frame, moves the editor to its line (the file is opened if it is a regular file of at most 64 MiB) and asks for the frame's `scopes`; the first scope that is not `expensive` opens by itself (`variablesView.ts:110-112`); every watch expression is evaluated with context `watch` for the frame. Other variables are asked for when the user expands them (lazy expansion through `variablesReference`). Picking another frame repeats the scopes and the watch evaluations for it and moves the editor.
10. **Versions instead of locks.** Execution moving on (`continue`, a step, a `continued` or `stopped` event) forgets the threads, frames, scopes and variables and drops every request still waiting for an answer about them from the table of pending requests; picking another frame drops the ones about the old frame. An answer that arrives later finds no request waiting and is ignored (`an answer nobody asked for`), so stale data is never applied. That also means a request an adapter never answers cannot pile up across stops. Console evaluations are kept: their answer is wanted whenever it comes.
11. **Bounds, since replies are hostile.** At most 64 threads, 100 frames, 8 scopes, 200 variables per reply, 2,000 nodes per tree, 32 watch expressions and 1,000 console lines; names, values and messages are cut at 500 characters; ids and references outside `0..=i32::MAX` are refused, and a variable that is not a string-named object is skipped; a variable can be expanded to depth 8 only, which ends an adapter's cycle of references; at most 256 requests wait for an answer and past that the client refuses with "the debug adapter has too many requests waiting"; a failed or cancelled `variables` request leaves the node empty, a failed `evaluate` shows the adapter's message as the watch's value or as a console error. A `continue` or step the adapter refuses reads the stop's state again and says why.
12. **Commands** use VS Code's ids and keys, each with VS Code's `when` clause (`debugCommands.ts:500-560`): `workbench.action.debug.stepOver` F10 (`debugState == 'stopped'`), `stepInto` F11 (`debugState != 'inactive'`), `stepOut` Shift+F11 (`debugState == 'stopped' && threadHasMultipleStackFrames`), `pause` F6 (`debugState == 'running'`). `Workspace::command_applies` evaluates the clause with the `rustode-config` evaluator, so the frontends hold no `when` logic: they ask it and, when it does not hold, the key keeps its other meaning. That resolves F6, which both frontends use for "focus next part": it pauses while the program runs and moves the focus otherwise. Watch commands: `workbench.debug.viewlet.action.addWatchExpression` and `debug.removeWatchExpression` (frontend prompts and selection), `workbench.debug.viewlet.action.removeAllWatchExpressions` (workspace), and the four focus commands `workbench.debug.action.focusCallStackView`, `focusVariablesView`, `focusWatchView` and `focusRepl`.
13. **Frontends.** TUI: a four-column panel below the editor while a session exists (`crates/tui/src/debug.rs`; Tab and Shift+Tab move between columns, Enter picks, opens or evaluates, Delete removes a watch, Escape leaves). GUI: the same four columns in egui (`crates/gui/src/debug.rs`); every row is a button for screen readers. The watch values and the console live in the workspace, so a restart of the frontend would lose nothing the session had.
14. **Tests.** `rustode-test-dap` grew a deterministic program language (`enter`, `leave`, `var`, `obj`, `global`, `print`, `error`, `console`, `WAIT`) that gives the call stack, the variables (objects nest, and one can point at itself), `evaluate` (`!cancel` fails with "cancelled", `!hang` is never answered), `next`, `stepIn`, `stepOut` and `pause`, and the option `--hostile-replies` that answers with oversized and malformed bodies. Tests: `crates/workspace/tests/dap.rs` (the workspace seam, including `what_arrives_after_execution_moved_on_is_dropped`, `a_reply_that_never_comes_is_bounded_and_does_not_block`, `hostile_replies_are_bounded_and_do_not_derail_the_session` and `a_cycle_of_objects_expands_only_to_the_depth_limit`), `crates/tui/tests/debug.rs` and `crates/gui/tests/frame/debug.rs` (snapshots of the stopped state with the four views).

## The guarantee

A debug adapter that crashes, refuses a request or sends garbage ends or ignores the one message, and never takes the editor down or loses an open document. Confirmed by `an_adapter_that_sends_garbage_does_not_derail_the_session`, `a_crashing_adapter_is_reported_and_the_workspace_goes_on` and `a_launch_the_adapter_refuses_ends_the_session_with_its_reason`.

## Consequences

- Not done, and for later tickets: attach requests; several threads at once (only the stopped thread's frames are shown, and its `threadId` is the one stepped and paused); stepping by instruction or into targets; editing a variable's value; paging of variables past 200 and of frames past 100; a console with history, completion and ANSI colors; the watch of a selected expression from the editor; mouse use of the TUI panel; compound configurations; the other launch variables; conditional breakpoints and logpoints; breakpoints that follow edits and survive a restart; a picker for the configuration (the first one runs until `select_launch_configuration` is called); mutation tests of the DAP parser (AGENTS.md §11.7.1 rule 7: the parser reads `serde_json::Value`, which is checked by the hostile-adapter tests only, now including `--hostile-replies`).
- `cargo xtask` scopes: the new crate has no scope of its own; its commits use `workspace`, as `test-lsp`'s do.
- Anything else that needs a different adapter lifecycle (restart on crash, several sessions) requires a new decision, not an extension of this one.
