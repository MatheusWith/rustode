# ADR 0031: Editor groups are a tree of splits in the workspace; one document, one history, and a cursor set for each view

- **Status:** accepted (2026-11-19, ticket 35)
- **Build:** rustode after `6eec957`; studied: the source tree of the App (local VSCodium 1.147.0)

## Context

Milestone M6 asks for split editors: horizontal and vertical splits, the same file editable in both panes, in both frontends ([ADR 0018](0018-phase-1-milestones.md)). Until now the workspace had one `EditorGroup` (the tabs) and every "active editor" feature (find, the minimap, language servers, the debug gutter, the status bar, quick open, search results opening, replace) read `Workspace::active_document`. [ADR 0014](0014-in-process-frontends.md) says the frontends hold no logic: the layout must come from the workspace.

## Decision

1. **The layout is a tree.** `Workspace::layout()` returns a `Layout`: a `Group(GroupId)` leaf, or a `Split { axis, children }` laid out side by side (`Axis::Horizontal`) or stacked (`Axis::Vertical`). Splitting goes right or down from the active group; a group added next to one whose parent splits the same way joins that parent, and any other split nests (`EditorPart.addGroup`, `src/vs/workbench/browser/parts/editor/editorPart.ts:674-700`; the grid in `src/vs/base/browser/ui/grid/`). Removing a group collapses a split left with one child and flattens a child split along its parent's axis. Group ids are never reused. `Workspace::group_ids()` lists the groups in grid order, which is what Ctrl+1, Ctrl+2 and "next group" count.
2. **Every group has its own tabs and active editor; one group is active.** `Workspace::tabs()`, `group()` and `active_document()` are the active group's, so everything that worked on "the active editor" keeps working on the active group's active editor. Opening a file opens it in the active group. The existing tests pass unchanged.
3. **A document stays open while any group shows it.** `Workspace::close_editor(group, id, discard)` closes one tab, and the document only when no other group shows it (and only then can it refuse with `Error::Dirty`). `Workspace::close(id, discard)` still closes the document everywhere. A group left with no editor closes unless it is the last, as `workbench.editor.closeEmptyGroups` (default true) does (`editorGroupView.ts:2053-2055`); closing a group that still has editors merges them into the most recently active other group (`doRemoveGroupWithEditors`, `editorPart.ts:894-907`), and the focus goes to the most recently active group (`doRemoveEmptyGroup`, `:909-917`).
4. **One document, one undo history, one cursor set per view.** The document's editor holds the selections of the active group. A group that loses focus keeps its own in `EditorGroup`'s `views`, only for documents another group shows, and gets them back when it regains the focus. Every edit, undo and redo is logged in chars (`rustode_core::CharEdit`, `Editor::record_char_edits`, on only while two groups share the document) and the kept selections are moved through the log: a point follows its text, a point inside deleted text lands where the deletion was, and an empty cursor at the place text is inserted moves after it, as when another view types there. `Workspace::view_selections(group, document)` answers per view, so a frontend draws the inactive pane's own cursors and selections. Undo and redo act on the document: the view that undoes gets the cursors the step stored, and the other views follow the splices.
5. **Commands** use VS Code's ids and default keys, registered in `COMMANDS` and run by `Workspace::execute`: `workbench.action.splitEditor` (Ctrl+\; to the right, or down when `workbench.editor.openSideBySideDirection` is `"down"`), `splitEditorRight` and `splitEditorDown`, `focusFirstEditorGroup`, `focusSecondEditorGroup` and `focusThirdEditorGroup` (Ctrl+1 to Ctrl+3; Ctrl+N one past the last group creates an empty group, `editorCommands.ts:694-718`), `focusLeftGroup`, `focusRightGroup`, `focusAboveGroup` and `focusBelowGroup` (Ctrl+K then Ctrl+arrow; they wrap, `editorActions.ts:280-292`), `focusNextGroup` and `focusPreviousGroup`, `moveEditorToNextGroup` and `moveEditorToPreviousGroup` (Ctrl+Alt+Right and Left), `closeEditorsInGroup` (Ctrl+K W), `closeGroup` and `joinAllGroups`.
6. **Key clashes.** Ctrl+W is `closeActiveEditor` while the active group has an editor (`!activeEditorGroupEmpty`) and `closeGroup` while it is empty with several groups (`activeEditorGroupEmpty && multipleEditorGroups`, `editorCommands.ts:866-870`); `Workspace::command_applies` evaluates both context keys, and a unit test fails when a group command shares a default key with another command that has no `when`. `splitEditorRight` and `splitEditorDown` have no default key: in the studied source they and `splitEditorLeft`, `splitEditorUp` and `splitEditorOrthogonal` all declare Ctrl+K Ctrl+\ (`editorActions.ts:107-181`), so the key cannot pick one of them.
7. **Frontends only render the layout.** Both walk `Workspace::layout()`, give every group a tab strip and an editor, and focus a group on a click. A split that cannot give every child its minimum shows only the child that holds the active group, so the width bands keep working: the TUI needs 30 columns per side-by-side group and 6 rows per stacked group, and shows one group below 60 columns of editor; the GUI keeps VS Code's 220-point minimum width and a tab strip plus 70 points of height per group (`editor.ts:30`). Snapshots cover every band.
   - TUI: one divider column between neighbors, the active group's tab underlined when it has no focus; keys Ctrl+\ (also Ctrl+4, which is how a terminal without the extended keyboard protocol sends it), Ctrl+1 to Ctrl+3, Ctrl+Alt+Left and Right, and the Ctrl+K chords.
   - GUI: only the active group's editor is interactive (it owns the focus, keys, overlays and minimap, under the same widget ids as before); another group's editor is painted with its own selections and scroll, scrolls with the wheel, and a press on it focuses the group and puts the caret there. Tab strips use ids of their own per group. An unfocused group's active tab is dimmed (`tab.unfocusedActiveForeground`, `tab.unfocusedActiveBorderTop`, `dark_modern.json:114`) and the divider is `editorGroup.border` (`dark_modern.json:36`).
8. **Bounds.** Group ids and sizes come from the layout only; frontends clamp what they draw (`Workspace::view_selections` clamps to the text, the TUI and the GUI clamp the scroll). Nothing indexes by a number from input.

## Consequences

- Not done, recorded in [G21](../gaps.md): the dividers do not drag and sizes are always equal; the inactive GUI pane has no minimap or hover; split left, up and orthogonal and "move into left/right/above/below group" are not registered; groups are not persisted; tabs cannot be dragged between groups.
- Scroll is frontend state keyed by group and document. It does not follow an edit made above it in another view.
- The cursor rule for text inserted exactly at another view's cursor (the cursor moves after it) is chosen for typing in two panes; whether VS Code does the same for a second view has not been measured here.
